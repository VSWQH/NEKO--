# N.E.K.O VRM 动作与语义贡献指南

> 适用范围：N.E.K.O 的 VRM 动作资产、压缩清单、本地语义识别和动作状态机。
>
> 当前对应：`Project-N-E-K-O/N.E.K.O#2712`（动作资产与播放器）和 `Project-N-E-K-O/N.E.K.O#2713`（语义动作运行时）。

## 1. 这套系统解决什么问题

N.E.K.O 不直接使用文件名或整段对话寻找动作。完整链路是：

```text
NEKO 回复或动作描述
    ↓
提取动作相关短句、身体部位、方向、姿态、情绪、程度和否定信息
    ↓
八国语言动作含义规范化为中文动作帧
    ↓
语义规则得到 intent（动作意图）
    ↓
动作清单根据 intent、姿态、情绪、风格、程度选择具体 VRMA
    ↓
校验 .vrma.gz → 首次播放时解压 → 播放 → 状态机处理衔接与回位
```

一个意图可以对应多个动作。例如 `nod` 可以同时拥有轻轻点头、自然点头、用力点头；运行时根据角色个性、当前情绪和程度选择，而不是为每个动作创建一套重复语义。

## 2. 两种贡献类型

### 2.1 为已有意图增加动作

适合：新增另一种点头、害羞、坐姿或休闲动作。

需要提交：

1. 一个经过验证的 `.vrma.gz`。
2. `manifest.json` 中的一张动作卡。
3. 对应资产与选择逻辑测试。
4. 来源和许可证证明。

通常不需要修改 `semantics.json`，应复用已有意图。

### 2.2 增加全新的动作意图

适合：动作库和语义库中都不存在的含义，例如现在没有“摸头安慰”的动作库和语义库，那就需要以下规范。

除上述内容外，还需要：

1. 在 `semantics.json` 中增加新规则。
2. 提供八国语言的常用动作表达。
3. 提供正例、反例和相似意图区分测试。
4. 说明新建意图而不复用已有意图的理由。

## 3. 动作资产要求

### 3.1 基本要求

- 格式必须为 VRM Animation（`.vrma`），内部为有效 GLB v2。
- 骨骼必须面向 VRM humanoid，不得绑定某一个角色的非标准骨骼。
- 动作不得出现 T-Pose、双臂突然水平伸直、模型瞬移或错误 Root Motion。
- 检查手臂、手腕、衣服和头发是否因绑定错误发生分离。
- 动作开始和结束应自然；不能依赖额外的固定 Pose 才能播放。
- `once` 动作播放后必须声明正确的结果姿态。
- `loop` 动作首尾应连续，不能每轮产生明显跳变。
- 坐、躺、趴等低姿态动作必须准确声明输入和结果姿态，以便状态机选择起身过渡。
- 至少在两种身高或体型不同的 VRM 模型上预览。

### 3.2 目录分类

| 目录 | 用途 | 例子 |
|---|---|---|
| `01_base` | 站立休闲、待机 | 自然站立、轻轻晃动 |
| `02_talk` | 交谈手势 | 点头、摇头、解释、制止 |
| `03_emote` | 情绪身体语言 | 害羞、生气、伤心、惊讶 |
| `04_social` | 社交动作 | 挥手、道歉、鼓掌、敬礼 |
| `05_pose` | 持续姿态 | 坐、盘腿、躺、趴、睡 |
| `06_activity` | 活动 | 弹琴、打字、操作平板 |
| `07_show` | 表演 | 舞蹈、展示动作 |
| `08_move` | 姿态过渡 | 从低姿态起身 |

不要根据个人习惯新建 `final`、`new`、`v2`、`其他` 等目录。

### 3.3 文件名和稳定 ID

文件名使用简短、能直接说明动作表现的中文：

```text
害羞地捂脸低头.vrma
坚定地用力点头确认.vrma
趴着安静熟睡轻微呼吸.vrma
```

不要使用：

```text
motion01.vrma
新动作最终版2.vrma
shy.vrma
```

每个动作还需要一个简短英文稳定 ID：

```text
shy_cover_face_01
nod_firm_01
sleep_prone_01
```

稳定 ID 一旦进入公开版本不得随意修改。显示名称可以改进，稳定 ID 用于用户配置、状态机和兼容迁移。

## 4. 压缩和完整性

仓库内置动作提交为 `.vrma.gz`，不同时保留未压缩副本。

在自动脚本补齐前，可使用确定性 gzip：

```bash
gzip -n -9 -c input.vrma > output.vrma.gz
shasum -a 256 input.vrma
shasum -a 256 output.vrma.gz
wc -c input.vrma output.vrma.gz
```

需要记录：

- `packedSha`：`.vrma.gz` 的 SHA-256。
- `decodedSha`：解压后 `.vrma` 的 SHA-256。
- `packedBytes`：压缩文件字节数。
- `decodedBytes`：解压文件字节数。
- `compression`：当前填写 `gzip`。

播放器会先校验压缩文件，再解压并校验原始 VRMA。任何一个哈希不一致都应拒绝播放。

```json
  "m": "shy",

  "packedSha": "<压缩文件 SHA-256>",
  "decodedSha": "<解压文件 SHA-256>",

  }

```

### 5.2 核心字段

| 字段 | 含义 |
|---|---|
| `id` / `card.stableId` | 永久稳定的资产 ID，二者必须一致 |
| `m` / `card.intent` | 动作意图，优先复用已有意图 |
| `f` | 解压后的逻辑路径；实际资产是该路径加 `.gz` |
| `in` / `inputPose` | 允许播放时的输入姿态 |
| `out` / `resultPose` | 动作完成后的姿态 |
| `mode` / `playback` | `once` 或 `loop` |
| `s` / `styles` | 风格标签，例如 `soft`、`firm`、`shy` |
| `i` | 程度：`1` 轻、`2` 中、`3` 强 |
| `body` | 动作实际控制的身体部位 |
| `emotions` | 适合的情绪，不等于语义本身 |
| `positiveZh` | 适合选择这个具体动作的中文描述 |
| `negativeZh` | 容易混淆但不应选择它的描述 |
| `ok` | 是否允许正式运行时使用 |
| `license` / `origin` | 分发依据和来源 |

## 6. 语义规则 `semantics.json`

### 6.1 什么时候新增规则

先依次检查：

1. 是否已有完全相同的 `intent`。
2. 是否只是同一意图的程度、情绪或姿态变体。
3. 是否可以通过动作卡的 `styles`、`emotions`、`i` 区分。

只有前三项都不能表达时才新增规则。不要为“轻点头”和“用力点头”各建一套完全重复的意图；它们应共享 `nod`，由程度选择动作。

### 6.2 示例

```json
{
  "id": "comfort_pat",
  "kind": "social",
  "priority": 86,
  "phrases": {
    "zh-CN": [
      "轻轻摸了摸你的头",
      "伸手揉揉你的头发",
      "温柔地拍了拍你的脑袋",
      "抬手轻抚你的头顶",
      "在你头上安慰地摸了摸",
      "掌心落在你的头顶",
      "轻轻顺了顺你的头发",
      "用手温柔地揉了揉你的头",
      "安慰似的拍了拍头",
      "小心地摸摸你的脑袋"
    ],
    "zh-TW": ["輕輕摸了摸你的頭"],
    "en": ["gently pats your head"],
    "ja": ["優しく頭を撫でる"],
    "ko": ["다정하게 머리를 쓰다듬는다"],
    "ru": ["нежно гладит тебя по голове"],
    "es": ["te acaricia suavemente la cabeza"],
    "pt": ["acaricia suavemente a sua cabeça"]
  },
  "aliases": {},
  "frames": {
    "zh-CN": [
      [["手", "手掌", "掌心"], ["摸头", "揉头发", "轻拍脑袋", "轻抚头顶"]]
    ]
  },
  "styles": {},
  "blocks": [
    "打头",
    "推开",
    "指着头",
    "检查头部",
    "自己摸头"
  ],
  "replaces": [],
  "emotion": "caring",
  "nameZh": "温柔地摸头安慰"
}
```

### 6.3 字段说明

| 字段 | 作用 |
|---|---|
| `id` | 与动作卡 `intent` 对应的短英文意图 |
| `kind` | `gesture`、`emotion`、`social`、`pose`、`activity` 等 |
| `priority` | 多条规则同时命中时的基础优先级；不能用极高优先级掩盖语义冲突 |
| `phrases` | 各语言中真实会出现的短动作表达 |
| `frames` | 身体部位、动作、方向等可组合证据，不要求整句完全匹配 |
| `blocks` | 明确排除相似但含义不同的文本 |
| `replaces` | 兼容被替换的旧意图，不用于普通同义词 |
| `emotion` | 可用于加分的官方情绪标识 |
| `nameZh` | 维护者可直接理解的中文意图名 |

## 7. 八国语言规则

当前支持：

```text
zh-CN、zh-TW、en、ja、ko、ru、es、pt
```

规则遵循：

1. `zh-CN` 是动作帧和动作卡的权威语言。
2. 其他语言只规范化动作相关含义，不翻译整段对话。
3. 不修改系统提示词、角色记忆、聊天框文本或朗读内容。
4. 八国语言显示名称必须全部存在。
5. 新意图至少应给每种语言一个可靠表达，并为主要目标语言补充真实变体。
6. `zh-CN` 与 `zh-TW` 分开维护，不依赖基础语言模糊回退。

## 8. 正例、反例和真实对话测试

每个新意图的中文短语不少于 10 个，但数量不是唯一指标。测试必须覆盖：

### 8.1 正例

- NEKO 常见的括号动作描述。
- 不带括号的自然叙述。
- 同一动作的简短、详细和含蓄表达。
- 身体部位与动作词分散在多个短句中的表达。
- 角色三种性格下常见的表达差异。

### 8.2 反例

- 含有相同单字但动作不同。
- 只讨论动作，没有实际执行。
- 否定、停止或拒绝执行。
- 用户自身的动作，不是 NEKO 的动作。
- 相似意图，例如挥手与摆手拒绝、捂脸害羞与捂脸哭泣。

### 8.3 连续计划

至少测试：

```text
动作 A → 动作 B
动作 A → 动作 B → 动作 A
坐着 → 躺下
趴着 → 起身 → 站立动作
短动作 → 恢复上一持续姿态
```

单轮最多三个动作。相同动作出现在不同位置时，不能因为去重而丢失后一次。

## 9. 本地测试

提交前至少运行：

```bash
node tests/frontend/vrm_motion_player.test.cjs
node tests/frontend/vrm_motion_policy.test.cjs
node tests/frontend/vrm_motion_semantics.test.cjs

uv run pytest tests/unit/test_vrm_motion_architecture.py -q
uv run pytest tests/unit/test_app_websocket_static.py -q
uv run pytest tests/frontend/test_jukebox_playback_modes.py -q

uv run pytest tests/unit -q
git diff --check
```

还应人工验证：

- 模型管理页面能显示八国语言动作名称。
- `.vrma.gz` 首次加载、解压和哈希校验成功。
- 动作可见，不出现 T-Pose 或手臂分离。
- 模型切换时旧动作不会继续控制新模型。
- 聊天开始、结束和中断不会造成循环、卡顿或旧动作覆盖新动作。
- 持续姿态不会无故回到站立。
- 低姿态之间切换不会先强制站立。
- 起身时使用过渡动作。
- 动作与表情可以同时生效，表情不应冻结身体动作。

## 10. 许可证和来源

每个动作必须满足以下条件之一：

- 贡献者原创，并明确允许随 N.E.K.O 公开分发和打包。
- 来自允许再分发、修改和商用的开源许可证。
- 获得版权所有者的书面授权。

必须提交：

- 原作者或贡献者名称。
- 原始项目或作品链接。
- 准确许可证标识和许可证文本位置。
- 是否修改、重定向或重新导出。

以下情况不得进入公开发行清单：

- 来源不明。
- 只有“网上下载”“可商用”的口头说明。
- 许可证允许使用但禁止重新分发源资产。
- 从商业平台下载且条款不允许把动作文件放进公开仓库。
- 去掉来源或许可证后重新声明为原创。

未知许可证资产应保持 `ok: false`，不能通过 `previewUnrated` 绕过正式发布限制。

## 11. PR 提交流程

1. Fork `Project-N-E-K-O/N.E.K.O`。
2. 从目标基础分支建立功能分支。
3. 一次 PR 只增加一个意图或一组强关联变体。
4. 添加压缩动作和动作卡。
5. 只有新增意图时才修改语义规则。
6. 添加正例、反例、I18N 和回归测试。
7. 运行完整测试。
8. 提交预览视频或 GIF，展示至少两个 VRM 模型。
9. 在 PR 描述中填写来源、许可证、姿态、程度和测试结果。
10. 根据审查意见修改后重新运行测试。

## 12. 维护者审核清单

- 稳定 ID 是否唯一且不会与现有用户配置冲突。
- 中文文件名是否能准确说明动作，而不是情绪猜测或模糊名称。
- 是否错误地新建了本可复用的意图。
- 动作卡和语义规则的 intent 是否一致。
- `inputPose`、`resultPose` 和实际动作是否一致。
- 轻、中、强程度是否与同意图的其他资产形成合理梯度。
- `blocks` 和反例是否覆盖最危险的误判。
- 八国语言是否是动作表达，而不是翻译整段对话。
- 压缩哈希、解压哈希和文件大小是否正确。
- 来源与许可证是否支持仓库和安装包再分发。
- 是否通过真实 Electron + VRM 播放验证，而不只是 JSON 分类测试。

## 13. 不应采用的贡献方式

- 只提交一个 `.vrma.gz`，没有动作卡、来源或测试。
- 根据文件名进行全文匹配。
- 每个动作文件都创建新的意图。
- 把所有相似表达塞进一个巨大正则。
- 只增加正例，不提供反例。
- 只测试直接命令，不测试 NEKO 自然聊天表达。
- 为动作识别修改系统提示词、角色记忆或聊天框文本。
- 通过额外 LLM 调用判断动作，增加 token 消耗。
- 用随机选择掩盖动作卡描述不完整。
- 修改稳定 ID 破坏已有用户设置。

## 14. 当前接口约定

- 本地动作判断不额外调用模型，单次动作额外 token 为 0。
- 动作判断只在 3D VRM 模式启用。
- 八国语言动作相关含义规范化为中文动作帧，但不会修改用户看到或听到的文本。
- 单轮动作计划最多三个动作。
- 清单未知动作返回 `no_motion`，不能使用未经批准资产作为正式回退。
- 压缩动作首次播放时解压并校验，不长期保留解压副本。
- 一个意图可对应多个动作，选择必须依据动作卡，不得在同一意图内盲目随机。
